Immutability, pattern matching, ADTs/enums, optionals and either/result types, lazy iterators, higher order functions, typeclasses and a lazy async ~effect~ future.

A point of contention would be giving space for both imperative and declarative code. A common critique raised towards Scala.

Let us compare a simple implementation for a user repository in both styles in Rust. As an added bonus let's use async traits for the main interface.

```rust
#[async_trait]
pub trait UserRepository: Send + Sync {
    async fn create(&mut self, user: User) -> Result<User, UserError>;
    async fn read(&mut self, user_id: Uuid) -> Result<User, UserError>;
    async fn update(&mut self, user: User) -> Result<User, UserError>;
    async fn delete(&mut self, user_id: Uuid) -> Result<User, UserError>;
}
```

For simple User Repository, let us first start by implementing a naive InMemory version before moving on to using some `sqlx` in a later post.
To keep things spicy, instead of using a Mutex lets use a RwLock to avoid excessive locking. In the future we could consider swapping the HashMap to a HashSet.

```rust
pub struct InMemoryUserRepository {
    users: Arc<RwLock<HashMap<Uuid, User>>>,
}

impl InMemoryUserRepository {
    pub fn new() -> Self {
        Self {
            users: Arc::new(RwLock::new(HashMap::new())),
        }
    }
}

#[async_trait]
impl UserRepository for InMemoryUserRepository {
    async fn create(&mut self, user: User) -> Result<User, UserError> { ... }
    async fn read(&mut self, user_id: Uuid) -> Result<User, UserError> { ... }
    async fn update(&mut self, user: User) -> Result<User, UserError> { ... }
    async fn delete(&mut self, user_id: Uuid) -> Result<User, UserError> { ... }
}
```

Now let's take a look at the first create method.


```rust
async fn create(&mut self, user: User) -> Result<User, UserError> {
    let mut map = self.users.write().await;
    match map.entry(user.uuid) {
        std::collections::hash_map::Entry::Occupied(_) =>
            Err(UserError::AlreadyExists(user.uuid)),
        std::collections::hash_map::Entry::Vacant(entry) => {
            entry.insert(user.clone());
            Ok(user)
        }
    }
}
```

Let's start simple, let's try to remove the explicit `Some(_)`. The change is simple, but the same way we can get rid of the notorious `Ok(())` at the end of many functions seen in Rust code. As a bonus we deal with Errors in a more explicit manner, the Error is not embedded in the depths of a closure.

```rust
async fn create(&mut self, user: User) -> Result<User, UserError> {
    let user_id = user.uuid;
    match self.users.write().await.entry(user.uuid) {
        std::collections::hash_map::Entry::Occupied(_) => None,
        std::collections::hash_map::Entry::Vacant(entry) => {
            entry.insert(user.clone());
            Some(user)
        }
    }
    .ok_or(UserError::AlreadyExists(user_id))
}
```

For the `read` function implementation, let's step up to full function chaining.

```rust
async fn read(&mut self, user_id: Uuid) -> Result<User, UserError> {
    let map = self.users.read().await;
    match map.get(&user_id) {
        Some(user) => Ok(user.clone()),
        None => Err(UserError::NotFound(user_id)),
    }
}
```

As a bonus let us use `_.cloned()`. Having everything happen in one function chain arguably removes cognitive load as we we construct and deconstruct values less.

```rust
async fn read(&mut self, user_id: Uuid) -> Result<User, UserError> {
    self.users
        .read()
        .await
        .get(&user_id)
        .cloned()
        .ok_or(UserError::NotFound(user_id))
}
```

For `update` lets switch it up a little bit, but again, sequential chaining makes the code easier to follow.

```rust
async fn update(&mut self, user: User) -> Result<User, UserError> {
    let mut map = self.users.write().await;
    if let Some(existing) = map.get_mut(&user.uuid) {
        *existing = user.clone();
        Ok(user)
    } else {
        Err(UserError::NotFound(user.uuid))
    }
```

Due to Rust's explicitness over calling borrowed values, we still have to sometimes create new values to reference them within the chain due to how closures work without passing along too much data in the annonymous function. The function chain gets quite long, but imaging more complex logic that needs to be handled inside imperative closures... And we haven't dealt with filters, flatMaps and or folds here either which make imperative code even harder to follow.

```rust
async fn update(&mut self, user: User) -> Result<User, UserError> {
    let user_id = user.uuid;
    self.users
        .write()
        .await
        .get_mut(&user_id)
        .map(|existing| *existing = user.clone())
        .map(|_| user)
        .ok_or_else(|| UserError::NotFound(user_id))
}
```

As a last, let's also take a look at `delete`:

```rust
async fn delete(&mut self, user_id: Uuid) -> Result<User, UserError> {
    let mut map = self.users.write().await;
    if let Some(user) = map.remove(&user_id) {
        Ok(user)
    } else {
        Err(UserError::NotFound(user_id))
    }
}
```

Function chaining again makes it a lot easier to follow what's happening.

```rust
async fn delete(&mut self, user_id: Uuid) -> Result<User, UserError> {
    self.users
        .write()
        .await
        .remove(&user_id)
        .ok_or(UserError::NotFound(user_id))
}
```

On closing note, forcing declarative style onto Rust might not fit everywhere, thus sometimes imperative declarations can make dealing with Rust's constraints easier, however functional chaining can drasticly reduce the amount of closure scopes and the amount of value declarations that add reasoning complexity. It's up to you to strike the balance is up to our taste.
